# Pre-Implementation Corrections

This document is the **baseline for implementation**. It records every correction made to the
Workshop 1 (Analysis) and Workshop 2 (Design) deliverables after a full consistency review, and states
explicitly what **changes** and what **is kept**.

- **Precedence:** where this document contradicts `Workshop-1/` or `Workshop-2/`, this document wins.
  The original PDFs, mockups and diagrams are kept unchanged as historical deliverables.
- **New files** produced by these corrections live in [`Updated-Files/`](Updated-Files/).
- **Language convention:** code and documentation are written in English. Text shown to end users
  (UI labels, status names, error messages, emails, PDFs) is in Spanish, because the target audience
  speaks Spanish. Example: the domain value `RECONCILED` is displayed as **"Conciliada"**.

**FR-02-05 (rewritten) — Hybrid virtual assistant.**
The public web portal provides a guided virtual assistant with three steps: contact details, products and
quantities, and summary. Step 1 requires full name, email and phone. In step 2 the customer selects active
catalog products and quantities. Optionally, they can also describe their needs in free text; the AI
(DeepSeek, behind the `ConversationalAssistant` port) turns that text into a **proposed** list of catalog
products and quantities. The customer must review and confirm that list in the structured form. Free text
never creates items directly, and products outside the active catalog are reported as unavailable. Once the
items are confirmed, the system estimates the price range, generates the PDF and offers download or email,
and records the quotation as "Pendiente de revisión". Conversations and free text are **not stored**. The
quotation and its PDF are the only results.

**FR-02-06 (changed) — Suggested dispatch date.**
The suggestion uses **only the historical median** (no buffers). It is calculated as follows:
- *Lead time* of a past order = `work_order.actual_dispatch_date − quotation.approved_at`.
- The median is computed per product and per quantity bucket. The buckets are **1–10, 11–50, 51–100 and more
  than 100** units.
- At least **3 samples** are required. Otherwise the message "Sin datos históricos suficientes para estimar la
  fecha de despacho" is shown and the Administrador must enter the date manually.
- For a multi-product quotation, the suggested date is the largest of the per-item medians.

The Administrador confirms or adjusts the date while reviewing the quotation. The Operador sees it on the O.T.

**FR-02-20 (rewritten) — Generate a Work Order from an approved quotation.**
From an approved quotation, the Operador uses **"Generar O.T."**. This is the only way to create an O.T.
- **Customer:** the quotation must be linked to an **active customer**. If it is not, the system requires the
  Operador to select an existing customer or register a new one first.
- **Items:** customer and items are copied from the quotation.
- **Delivery date:** the agreed delivery date defaults to the quotation's dispatch date.
- **Number and status:** the system assigns a unique consecutive O.T. number and sets the status to
  "Pendiente".
- **Audit:** the creation is logged in the audit log.
- **One O.T. per quotation:** a second O.T. for the same quotation is rejected.

**FR-02-24 (new) — WhatsApp price history import.**
Users with `PRICE_HISTORY_IMPORT` (Administrador, Superadministrador) can upload an exported WhatsApp chat:
`.txt` (preferred) or screenshots. The AI extracts candidate price samples with these fields: product text,
quantity, unit price and message date. The samples stay in "pending review" until the user matches each one
to a catalog product and confirms it, or discards it. Only confirmed samples feed the price estimator, and only
when there are not enough recent approved quotations. The original file is deleted after extraction, and
samples keep no personal data (Law 1581 of 2012).

### 5.3 Architecture diagram

**Kept:** hexagonal architecture (ports and adapters), deployed as a modular monolith, client-server
communication, REST API with Django REST Framework, Celery Beat for scheduled backups,
PostgreSQL as the single database.

**Changes**

| Element | Change |
|---|---|
| Chatbot Controllers (WebSocket / Django Channels) | **Replaced by REST controllers.** The guided assistant needs no persistent connection. Django Channels is removed. |
| `Session` + `SessionRepository` + `PostgresSessionRepository` | **Added.** See the note below. |
| Price history import module | **Added:** controller, `PriceHistoryImportService`, ports `PriceSampleExtractor` and `PriceSampleRepository`, adapter `DeepSeekPriceSampleExtractor`. |
| Isolated restore environment (sandbox) | **Missing adapter**, see [Open items](#7-open-items). |
| Clients | The web clients are a React SPA (see [6.2](#62-frontend)). |

> **Why `SessionRepository`?** FR-01-05 (one active session) and FR-01-06 (15-minute inactivity) cannot be
> enforced with stateless JWTs alone: a token stays valid until it expires. So every request must check that
> its session is still `ACTIVE`, and every login must close the previous session. The `Session` domain
> entity models that. `SessionRepository` is the outbound port the application uses to load, save and
> terminate sessions, and `PostgresSessionRepository` is its adapter. The current diagram has the `SESSION`
> table and the `Session` class, but no port or adapter connecting them.

| `SESSION` | `access_token_id` is not stored (the access token carries the session id). Termination reasons add `PASSWORD_CHANGED` and `TOKEN_REUSE` (replayed refresh token). |
| `TOTP_ENROLLMENT` | The TOTP secret is stored encrypted (Fernet) in `encrypted_secret`; `last_used_step` prevents reusing a code. The QR image is generated on demand, not stored. |
| `PRICE_IMPORT_BATCH` | **New** table. |
| `HISTORICAL_PRICE_SAMPLE` | **New** table. |
| Timestamps | `timestamp` → `timestamptz` everywhere (NFR-08-01 requires the time zone). |

**Why a nullable `user_id` plus `actor_type`?** Some audited actions have no user account behind them: the
scheduled backup (`SYSTEM`), quotations created by the public assistant, and failed logins with an unknown
email (`ANONYMOUS`). The alternative, a fake "system user" row, was rejected: it pollutes user management and
would be an account that could, in principle, log in.

## 6. Technology and deployment decisions

### 6.1 Backend

Kept as designed: Python + Django + Django REST Framework, Celery + Celery Beat, PostgreSQL,
hexagonal architecture.

Changed: **SimpleJWT is replaced by PyJWT behind the `TokenIssuer` port** (adapter `JwtTokenIssuer`,
as in the class diagram). SimpleJWT requires Django's own user model and has no pre-authentication
token for the 2FA step; with PyJWT the access token carries the session id, which is checked against
the `SESSION` table on every request (single session and inactivity, FR-01-05/06). The refresh token
travels in an `httpOnly` cookie and the access token is kept only in the browser's memory.

**Roles are stored as a column of `APP_USER`.** Because roles and their permissions are fixed
(RN-M1-01, FR-01-04), the role-permission matrix lives in code (`shared_kernel.domain.security`)
instead of the `ROLE` / `ROLE_PERMISSION` tables of the corrected model, so there is nothing to keep in
sync.

Changed: **Django Channels and WebSockets are removed** (the assistant is REST-based). Redis is still needed
as the Celery broker.

Modules follow the names of the architecture diagram (Auth, User Account, Product, Customer, Chatbot,
Quotation, Work Order, Accounting Export, Backup) plus the Shared Kernel and the new **Price History**
module (WhatsApp import, FR-02-24), which is added to the diagram as a tenth business module.

**API documentation:** the OpenAPI 3 schema is generated automatically from the REST views and serializers
with **drf-spectacular**, and published with Swagger UI (`/api/docs/`) and ReDoc (`/api/redoc/`).

### 6.2 Frontend

**Decision: SPA (single-page application) with CSR (client-side rendering).**

| Option evaluated | Navigation / rendering | Result |
|---|---|---|
| Django templates + HTMX | MPA + SSR | Rejected: the design is API-first (REST + JWT); the API would be duplicated by server views. |
| **React + TypeScript + Vite** | **SPA + CSR** | **Chosen**: consumes the REST API directly; suits highly interactive screens (filters, multi-step flows, multi-selection, inactivity timer based on clicks/scroll); no SEO needs (internal app behind login). |
| Next.js | SPA + SSR | Rejected: adds a Node server that duplicates Django's role; its benefits (SEO, faster first paint) do not apply. |

Proposed libraries (to be confirmed when the skeleton is built): React Router, TanStack Query,
React Hook Form + Zod, Tailwind CSS + shadcn/ui.

### 6.3 Hosting

Hosting is not a requirement this semester.

- **Decision: local first.** The whole system (frontend, backend, workers, database) runs together on one
  machine with Docker Compose. Every team member runs it locally during development.
- **Optional, later:** the same Compose setup can be copied to a rented Linux server (VPS) for demos.
  Platforms designed for a single service (Render, Railway, etc.) are not a good fit because the system has
  several services.
- **GitHub Pages is not used.** It only hosts static files, so it could serve the built React app but **not**
  the backend (Django, Celery, PostgreSQL, Redis), which needs a machine that runs processes. Keeping
  everything on one host avoids cross-origin (CORS) setup and SPA routing workarounds.
